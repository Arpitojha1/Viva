## Task 1 — Resume parse cache (dedup on re-upload)

**Problem:** re-uploading the same resume re-runs the Groq extraction call
every time, even though nothing changed.

**Pattern to follow:** mirror the exact-hash dedup already implemented for
book ingestion (`ingested_books.file_hash`). Do not invent a new pattern.

**Do:**
- Add `content_hash VARCHAR(64) UNIQUE` to `resumes`, computed from the
  extracted raw text (post-extraction, not the raw PDF bytes, so formatting-
  only re-exports of the same resume still dedup correctly).
- Before calling Groq for structured extraction, hash the extracted text and
  check for an existing `resumes` row with that hash. If found, reuse its
  `extracted_skills` and skip the LLM call.
- Write an Alembic migration for the new column + unique index.

**Explicitly out of scope:** semantic/near-duplicate resume matching (like
the `SIMILARITY_DEDUP_THRESHOLD` book logic). Exact-hash only for now — two
resumes that differ by one line should NOT be treated as identical.

---

## Task 2 — Question bank reuse (with a scope guard)

**Problem:** every question is generated fresh, even for concepts that have
already produced a question for a prior candidate at the same difficulty.

**Constraint to respect:** do not cache adaptive follow-up questions. Those
are grounded in a specific candidate's answer trajectory and are the actual
product differentiator — caching them turns the interview into a static test
bank, which is a worse product, not just a cheaper one.

**Do:**
- New table `question_bank`: `id, chunk_ids INT[], difficulty, question_text,
  times_served INT DEFAULT 0, created_at`.
- Only the **first-attempt, non-adaptive** question generation path (i.e.
  `is_adaptive_followup = FALSE`) checks this table before calling Groq: look
  up by `(chunk_ids, difficulty)`, and if `times_served < N` (start with
  N=3, make it configurable), serve the cached question and increment the
  counter instead of generating.
- Adaptive follow-ups (`is_adaptive_followup = TRUE`) always generate fresh,
  no exceptions.
- Log which path was taken (cache hit vs. generated) so token savings are
  measurable afterward, not just assumed.

## Task 3 — Scoring pipeline: make `numeric_score` real

**Problem:** `numeric_score` is currently only ever 35, 65, or 90 — it looks
like a fixed mapping from the `quality_score` enum (`weak/ok/strong`) rather
than a genuine output of the scoring model. This is why scoring feels
"mocked" even though the category judgment itself is reasonable.

**Do:**
- Change the scoring prompt (the 8B-instant call) to require a numeric score
  0–100 directly from the model, alongside its reasoning — not a category
  that then gets remapped to a constant.
- Derive `quality_score` (`weak/ok/strong`) FROM the numeric score via
  fixed thresholds, for display/filtering purposes — category becomes a
  label on top of the real number, not the source of truth.
- Confirm `score_reasoning` is being populated with real per-answer
  reasoning (it exists in the schema — verify it's actually being written,
  don't assume).
- Do NOT change the scoring model (stay on 8B-instant) — this is a prompt/
  parsing fix, not a model-tier change.

## Task 4 — Interactive performance/summary page

**Problem:** the summary page is a static chart. It should let you see how
the candidate's performance moved question-by-question, and why.

**Do:**
- Change the summary endpoint to return the full ordered per-question
  series, not a pre-aggregated result: `[{order_index, difficulty,
  question_text, numeric_score, quality_score, score_reasoning, chunk_ids}]`
  for every question in the session.
- Frontend: render this as an interactive line/step chart (score over

  question's text, the candidate's answer, the score, and the reasoning.
  Do the aggregation client-side from the full series — don't pre-collapse

  frontend; this is a data/interactivity change, not a redesign.

## Task 6 — Security hardening before public deploy

This app has no auth in scope (`users.id` nullable, no auth per schema
comments) and is about to be deployed publicly (Railway + Vercel, per the
handoff doc). Fix the following before that deploy, not after:

**6a. Session ID exposure (IDOR)** — `sessions.id` is a sequential SERIAL PK
exposed directly in API routes. Anyone can enumerate session IDs and pull
another candidate's summary/answers. Generate a UUID/opaque token per
session for use in URLs and API routes; keep the serial PK internal only.

**6b. Resume text is untrusted LLM input** — resume text goes straight into
prompts (extraction, and likely question generation context). Treat it
explicitly as data, not instruction, in the prompt template (e.g. wrap it in
clear delimiters and instruct the model to treat content within them as
reference text only, never as instructions to follow). This is a prompt
hardening task, not a full injection-detection system — don't over-build it.

**6c. Rate limiting** — no rate limiting currently exists on `/api/session`
or `/api/resume`, meaning the public deploy has an open path to burn the
Groq quota. Add basic per-IP rate limiting at the FastAPI layer (`slowapi` or
equivalent) on resume upload and session creation specifically — these are
the two endpoints that trigger LLM calls.

**6d. CORS** — confirm `ALLOWED_ORIGINS` is set to the actual deployed
Vercel domain before going live, not a wildcard. This is a config check, not
a code change — verify `.env` for the deployed environment explicitly.

## Task 7 — Investigate duplicate call bug

Two Groq calls fired 205ms apart with byte-identical 1304-token input on the
70B model during testing. This needs root-causing before assuming Tasks 1–2
will fix the token burn on their own — if something is double-firing
requests, caching will just mean you cache-hit twice instead of
generating twice, which still isn't free.

**Do:**
- Check for React double-invoke in dev (StrictMode double-effect firing a
  fetch twice) on whichever frontend action triggers this call.
- Check for any client-side retry-on-slow-response logic that isn't
  idempotent (i.e. retries by firing a new request rather than polling the
  original).
- Report which one it was (or a different cause) before closing this task —
  don't just "add debouncing" as a blind fix without confirming the actual
  trigger.
